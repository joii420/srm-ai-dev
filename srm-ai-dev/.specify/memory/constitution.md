# SRM AI 项目宪章

## 核心原则

### 一、规格驱动开发

所有功能开发必须（MUST）在实现之前以正式规格说明书开始。
规格说明书定义用户故事、验收标准和成功指标。在规格说明书
通过审查和批准之前，不得编写任何代码。

- 每个功能必须（MUST）在实现开始前获得批准的 `spec.md`。
- 规格说明书必须（MUST）包含按优先级排列的用户故事（P1、P2、P3），
  且每个用户故事可独立测试和交付。
- 需求必须（MUST）使用精确语言（遵循 RFC 2119 的 MUST、SHOULD、MAY）
  ——禁止使用"应该表现良好"等模糊表述。
- 对已批准规格说明书的变更必须（MUST）经过澄清流程
  （`/speckit.clarify`）并重新获得批准。

**原理**: 规格优先开发在昂贵的实现开始之前消除歧义，减少返工，
并确保每一行代码都可追溯到经过验证的需求。

### 二、测试优先开发（不可协商）

所有实现必须（MUST）遵循测试驱动开发（TDD）。测试在生产代码
之前编写，先验证测试失败，然后使其通过。

- 测试必须（MUST）在相应实现编写之前编写，且必须（MUST）先失败。
- 必须（MUST）严格遵循"红-绿-重构"循环：
  编写失败测试 → 实现最少代码使测试通过 → 重构。
- 每个用户故事必须（MUST）至少有一个端到端集成测试来验证
  完整流程。
- 每个公开 API 端点或服务间边界必须（MUST）存在契约测试。
- 任何提交都不得（MUST NOT）降低测试覆盖率。

**原理**: TDD 产生的代码在构建时即正确，通过测试用例自文档化，
且可安全重构。跳过测试会产生隐性技术债务，并在功能间不断累积。

### 三、模块化架构

代码必须（MUST）组织为边界清晰的模块，具有显式依赖和单一职责。

- 每个模块必须（MUST）有单一、明确的用途——禁止使用
  "utils" 或 "helpers" 等万能模块。
- 模块之间不得（MUST NOT）存在循环依赖。
- 模块间通信必须（MUST）通过定义的接口（契约）进行，
  绝不允许直接访问内部实现。
- 新模块必须（MUST）能够独立测试，无需运行完整应用。
- 禁止模块间共享状态；数据通过显式参数和返回值传递。

**原理**: 模块边界防止耦合，支持跨用户故事的并行开发，
并使单个组件可替换而不产生级联变更。

### 四、可观测性与结构化日志

所有服务和重要操作必须（MUST）产生结构化、可查询的日志输出，
使调试无需依赖调试器即可进行。

- 日志条目必须（MUST）为结构化格式（JSON），使用一致的
  字段名：`timestamp`、`level`、`message`、`context`。
- 每个面向用户的操作必须（MUST）记录其开始、完成和
  所有错误，并提供足够的上下文以重现问题。
- 错误日志必须（MUST）包含：操作名称、输入摘要、错误
  类型和堆栈跟踪。
- 日志级别必须（MUST）遵循：ERROR（需要关注的故障）、
  WARN（功能降级但仍可用）、INFO（业务事件）、
  DEBUG（开发详情）。
- 敏感数据（令牌、密码、PII）绝不可（MUST NEVER）出现在日志中。

**原理**: 当生产问题发生时，日志是主要的诊断工具。结构化日志
支持自动告警、可搜索的事件响应和审计追踪。

### 五、简洁性与 YAGNI 原则

每一段代码都必须（MUST）针对当前的具体需求证明其存在价值。
禁止推测性泛化。

- 在至少存在两个具体用例之前，不得（MUST NOT）引入抽象——
  三行相似的代码优于一个过早的抽象。
- 不得（MUST NOT）为假设的未来需求添加配置和功能开关。
- 必须（MUST）评估依赖的必要性；当能力相当时，优先使用
  标准库而非第三方包。
- 代码审查必须（MUST）质疑任何无法追溯到当前规格说明书中
  需求的新增内容。
- 如果存在更简单的方案能满足所有当前需求，则必须（MUST）
  选择更简单的方案。

**原理**: 复杂性是可维护性的头号敌人。未使用的抽象、推测性
功能和不必要的间接层会减慢开发速度并模糊意图。

## 技术约束

- **运行时**: Node.js（LTS 版本）
- **语言**: TypeScript 严格模式（`tsconfig.json` 中 `strict: true`）。
  除经过验证的系统边界（如解析外部 JSON）外，禁止使用 `any` 类型。
- **包管理器**: npm（锁文件必须（MUST）提交）。
- **测试框架**: 必须支持单元测试、集成测试和契约测试的分离，
  具有清晰的目录结构（`tests/unit/`、`tests/integration/`、
  `tests/contract/`）。
- **代码检查/格式化**: ESLint + Prettier。所有代码必须（MUST）在
  提交前通过代码检查。禁止在无内联说明注释的情况下禁用检查规则。
- **构建目标**: ESM 模块。新代码不得（MUST NOT）使用 CommonJS。
- **最低 Node 版本**: 在 `package.json` 的 `engines` 字段中定义，
  并由 CI 强制执行。

## 开发工作流

- **分支策略**: 按规格说明书创建功能分支
  （`specs/[branch-name]/`）。所有工作在功能分支上进行；
  禁止直接提交到 `main`。
- **提交纪律**: 提交必须（MUST）是原子性的（每次提交一个逻辑变更），
  并使用遵循约定式提交格式的描述性消息
  （`feat:`、`fix:`、`test:`、`docs:`、`refactor:`）。
- **代码审查**: 每个 PR 在合并前必须（MUST）经过审查。审查
  必须（MUST）验证：
  1. 测试存在且遵循 TDD（在实现之前编写）。
  2. 无宪章违规。
  3. 无不必要的复杂性。
  4. 重要操作已具备结构化日志。
- **CI 流水线**: 所有 PR 在允许合并前必须（MUST）通过：
  代码检查、类型检查、单元测试、集成测试和契约测试。
- **完成定义**: 用户故事在以下条件全部满足时视为完成：
  - 规格说明书中的所有验收场景通过。
  - 测试通过且覆盖率未降低。
  - 所有重要操作的日志已就位。
  - 代码审查已批准。

## 治理

本宪章是 SRM AI 项目开发实践的最高权威。所有其他指南、惯例
和临时决策均从属于本宪章。

- **至上性**: 当本宪章与其他文档冲突时，以本宪章为准。
- **合规性**: 每个 PR 和代码审查必须（MUST）验证对所有原则的
  遵守。不合规问题必须（MUST）在合并前标记并解决。
- **修订**: 对本宪章的变更需要：
  1. 描述变更及其理由的书面提案。
  2. 项目负责人的审查和批准。
  3. 受变更影响的现有代码的迁移计划。
  4. 遵循语义化版本控制的版本递增（见下文）。
- **版本策略**:
  - MAJOR: 原则的删除或不向后兼容的重新定义。
  - MINOR: 新原则或实质性扩展的指导。
  - PATCH: 澄清、措辞修正、非语义性改进。
- **复杂性论证**: 任何偏离简洁性原则的情况必须（MUST）在计划的
  复杂性跟踪表中记录理由和被拒绝的替代方案。
